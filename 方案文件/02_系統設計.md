# 系統設計

> 對應程式：`程式/`（Node.js 24，零外部依賴）

## 一、整體架構

```
        學生平板／手機                        老師電腦
              │                                  │
              └──────────┬───────────────────────┘
                         │  HTTP（同一個 WiFi，瀏覽器開啟）
                         ▼
        ┌────────────────────────────────────┐
        │  node server.js（單一進程）         │
        │                                    │
        │  /            靜態頁（HTML/CSS/JS） │
        │  /api/*       JSON API             │
        │  /api/files/* 學生相片（有權限檢查） │
        │                                    │
        │  lib/auth.js   密碼與 session       │
        │  lib/db.js     建表與示範資料        │
        │  lib/api.js    全部端點            │
        │  lib/ai.js     AI 預批（可換供應商） │
        └───────────┬────────────┬───────────┘
                    │            │
             app.db（SQLite）   uploads/（相片檔）
                    │
                    ▼
        AI 供應商（OpenAI 兼容 API，可選）
        DeepSeek / 通義千問 VL / GLM-4V / 本地 Ollama
```

**為甚麼是單一進程**：試用規模是一個班、同時在線不超過 40 人。
單進程＋SQLite 足夠，而且「複製一個資料夾就能搬去另一台機」對學校環境很重要。

## 二、技術選擇與理由

| 選擇 | 理由 | 代價 |
|---|---|---|
| Node.js 24 內建 `node:sqlite` | 零外部依賴，不用 `npm install`，不怕學校電腦裝不到套件 | 仍是實驗性 API，升級 Node 要留意 |
| 無框架（`node:http`） | 全部程式碼自己看得到，出事容易查 | 要自己寫路由與 multipart（本版改用 base64 JSON 上傳，繞過 multipart） |
| 無 build step 的前端 | 老師的電腦不需要 Node 以外的工具鏈；改一個字即時生效 | 程式碼較長，沒有 TypeScript 型別檢查 |
| 圖片在瀏覽器壓縮（canvas，長邊 1600px、質素 0.82） | 學校 WiFi 上傳 8MB 原圖很慢；1600px 已足夠看手寫字 | HEIC 相片部分瀏覽器解不開，需要提示學生轉 JPG |
| 密碼 scrypt + 隨機 salt | Node 內建，足夠 | 沒有加二次驗證（試用期不需要） |
| Session 存 DB（HttpOnly Cookie） | 老師可以一鍵「踢走」某學生（解除註冊時同時刪 session） | 沒有 JWT 的無狀態好處 |
| AI 用 OpenAI 兼容協議 | 換供應商只改 `config.json` 三行 | 各家回覆格式略有差異，已做容錯解析 |

### 實測：網路磁碟不適合放資料庫

程式原本打算放在學校的 `V:`（實際是 `\\data.mkpc.edu.hk\Data\...` 網絡磁碟）。
實測 SQLite 寫入約 **25 ms／次**（本機通常 <1 ms）：

```
200 次連續 INSERT：5,027 ms（網絡磁碟）
```

所以：
- **程式與文件**可以放在網絡磁碟（方便備份、共用）；
- **資料庫與相片**建議放本機（`程式/data/`），定期備份上網盤。
- 已把多次寫入包進 transaction，減少 fsync 次數。

> 若一定要放在網絡磁碟，功能仍可運作（實測 WAL 模式可用），
> 但一個班同時提交時會感到慢。

## 三、資料模型

```
roster（老師匯入的權威名單）
  id, class_name, class_no, name, student_no(唯一), claimed_by → users.id
        │
        │ 學生註冊時核對 student_no + name + class_name
        ▼
users
  id, role(teacher|student), login_id(唯一), name, class_name, class_no,
  student_no, password_hash, roster_id, active

assignments（作業）
  id, title, subject, class_name, description,
  questions_json  ← 題目與評分點（見下）, total_score, due_at,
  status(draft|open|closed), allow_late

submissions（一份提交）
  id, assignment_id, student_id, status, submitted_at, late,
  ── AI 的結果 ──   ai_json, ai_total, ai_confidence, ai_model, ai_at
  ── 老師的結果 ── teacher_scores_json, teacher_total, teacher_comment,
                   teacher_notes, graded_by, graded_at, returned_at
  ── 學生提問 ──   question_text, question_at
  UNIQUE(assignment_id, student_id)   ← 一人一份，重交是覆蓋

answers   (submission_id, q_no, answer_text)     文字作答
files     (submission_id, q_no, filename, mime, size, sha256)   相片／PDF
sessions  (token, user_id, expires_at)
audit     (actor_id, action, target, detail, created_at)        操作記錄
```

### 題目與評分點的結構（`questions_json`）

```json
[{
  "no": "3",
  "tag": "實驗設計",
  "type": "text_photo",
  "prompt": "老師給你兩杯透明液體…請設計一個實驗分辨它們…",
  "max": 6,
  "points": [
    { "id": "3-1", "desc": "提出可行的分辨方法", "score": 3 },
    { "id": "3-2", "desc": "步驟寫得清楚，其他人可以照著重做", "score": 2 },
    { "id": "3-3", "desc": "有拍照記錄實驗裝置", "score": 1 }
  ]
}]
```

**為甚麼要這樣拆**：這是整個系統的支點。

- AI 有明確的給分單位 → 不會「整體感覺 4 分」；
- 老師覆核時看的是「這一點給唔給」，比重新想一次快；
- `tag` 讓每次評分自動累積成知識點數據。

## 四、一份作業的狀態流轉

```
                     老師建立作業
                          │
                    ┌─────┴─────┐
                 draft        open ◄────── 老師可隨時開關
                （學生看不到）    │
                          ┌───────┴────────┐
                     學生提交            逾期（標記 late）
                          │
                     submitted ──老師按「AI 預批」──► ai_graded
                          │                              │
                          │                        老師逐題定分
                          │                              │
                          └──────────┬───────────────────┘
                                     ▼
                                 returned ──學生提問──► questioned
                                     │                      │
                                老師可再改分／回覆 ◄─────────┘
```

規則：

- 發還後學生不能再直接重交（避免「見到分數再改答案」）；
- 老師可「重開」讓學生重做；
- 截止前重交會覆蓋舊版本，並清掉舊的 AI／老師分數。

## 五、AI 預批的設計

### 5.1 送給模型的是甚麼

```
系統提示：你是一位香港小學科學科老師的批改助手…（7 條規則）
使用者訊息：
  【作業】單元一 物質的變化 · 實驗記錄（小學科學 5B）
  【題目與評分點】
    第 1 題（滿分 4 分，知識點：觀察與記錄）
      題目：…
      評分點：1-1（2 分）…／1-2（2 分）…
  【學生作答】
    第 1 題：鹽粒越攪越小…
    第 3 題：…（另有 1 張照片，見下）
  [圖片]（若配置了視覺模型）
```

### 5.2 要求模型回傳的格式

```json
{
  "questions": [{
    "no": "1", "confidence": 0.85, "comment": "兩個現象都寫到了。",
    "points": [{ "id": "1-1", "awarded": 2, "evidence": "學生寫「鹽粒越攪越小」，對應評分點" }]
  }],
  "flags": ["需老師覆核：第 3 題 —— 照片反光，看不清楚裝置"],
  "summary": "概念掌握良好，實驗步驟可再具體。"
}
```

### 5.3 伺服器端會再做一次對齊（`normalizeResult`）

模型偶爾會漏掉評分點、編造 id、給出超額分數。伺服器一律：

- 只接受老師定義過的 `id`；
- 分數夾在 `0..該點滿分`，以 0.5 為單位；
- 缺漏的評分點補 0，並自動加 flag；
- 總分由伺服器自己加總，**不信任模型報的總分**；
- 信心值取所有題目最小值（寧可提示老師多看）。

### 5.4 沒有視覺模型時

作業有照片但沒配置 `visionModel`，系統會叫模型「凡涉及照片的評分點給 0，並標記需老師看圖」。
這樣分數不會假裝看過圖，老師一定會被告知。

### 5.5 模擬模式

沒有 API Key → 用本地規則產生「明顯是假的」分數（按字數粗估、信心 20%、
每點依據都寫「模擬模式」），並在介面最上方顯示橙色警告。
用途只有一個：讓流程可以被完整走一次，而不會被誤認為 AI 真的批改過。

## 八、部署與備份

### 啟動

```
1. 安裝 Node.js 22.5 或以上（本機測試用 24.16）
2. 雙擊 程式/start.bat
3. 瀏覽器開 http://127.0.0.1:8787
4. 學生用同一個 WiFi，開伺服器顯示的區網網址（例如 http://192.168.1.23:8787）
```

### 接上真實 AI

編輯 `程式/config.json`：

```json
{ "ai": { "baseUrl": "https://api.deepseek.com/v1", "apiKey": "sk-...", "model": "deepseek-chat" } }
```

要處理照片題，再加視覺模型：

```json
{ "ai": { "visionModel": "qwen-vl-max", "baseUrl": "https://dashscope.aliyuncs.com/compatible-mode/v1" } }
```

> 視覺模型與文字模型可以來自不同供應商，但本版只支援同一組 `baseUrl`。
> 如果學校封鎖外部 API，可改用本機 Ollama（`baseUrl: "http://127.0.0.1:11434/v1"`）。

### 備份

- 資料全部在 `程式/data/`（`app.db` + `uploads/`）；
- 用 `node scripts/backup.mjs` 產生 `備份與匯出/backup-YYYYMMDD-HHMM.zip`；
- 建議每天放學後執行一次，或排程在 17:00；
- 學期尾把整個 `data/` 壓縮封存，然後清空 `app.db` 重新開始。

## 九、已知限制（試用期可以接受，但要知道）

1. **沒有 HTTPS**：區網明文傳輸。試用期可接受，對外一定要加。
2. **每人一份提交**：不支援「多檔案版本歷史」，重交即覆蓋。
3. **圖片不能線上標註**：老師不能直接在相片上畫圈，只能寫文字評語。
4. **知識點靠老師手打**：沒有統一詞表，同一個概念打錯字就會分開統計。
5. **AI 不判「字跡」**：手寫潦草不會被扣分，也不會被讀懂。
6. **單機**：伺服器關掉學生就交不到，建議用課室電腦長開。
7. **沒有家長端**：家長只能透過學生帳號看。

## 十、v0.2 改動（接上真實模型之後）

### 10.1 AI 由「一個函式」變成「六個能力」

`lib/ai.js` 現在提供：`transcribeImage`、`gradeSubmission`、`draftComment`、
`suggestAssignment`、`classInsight`、`askAboutFeedback`。
共用一個 `chat()` 核心，統一處理重試、超時、推理 token、JSON 容錯。

### 10.2 新增的資料欄位

```
answers:  mode            'typed' | 'photo'
          transcript      AI 轉寫原稿（永不覆蓋）
          transcript_confidence / transcript_notes / transcript_uncertain
          corrected_text  老師修正版 ← 評分用這一份
assignments: term, level
submissions: ai_usage    每次 AI 的 token 與耗時
新表 ai_calls          每一次模型呼叫（用途、tokens、耗時、錯誤）
```

**為甚麼要分成 `transcript` 與 `corrected_text`**：學生寫的和系統讀到的可能不同，
老師改過的又是第三個版本。三個都要留，否則日後無法回答「為甚麼這句被扣分」。

### 10.3 新增端點

| 方法 | 路徑 | 作用 |
|---|---|---|
| POST | `/api/submissions/:id/transcribe` | 重新辨識手寫 |
| POST | `/api/submissions/:id/correct` | 老師修正轉寫稿 |
| POST | `/api/submissions/:id/comment-draft` | 評語草稿 |
| POST | `/api/submissions/:id/ask` | 學生追問（不改分） |
| POST | `/api/ai/suggest` | 出題助手 |
| GET | `/api/assignments/:id/insight` | 班級洞察 |
| GET | `/api/ai/usage` | AI 用量與健康度 |

### 10.4 作文的雙通道

題目類型多了一個 `essay`：學生提交時自己選「打字」或「拍照」。
選拍照的，提交後**伺服器即時轉寫**（約 2–3 秒），老師打開批改頁時已經見到文字。
轉寫只對 `essay` 題做——其他題目讓模型直接看圖，不需要多一層轉換。

### 10.5 可靠性

- 推理模型 `finish_reason: length` → 自動加倍 `max_tokens` 重試一次；
- 純文字任務（評語、分析、追問）不强制 JSON，少一個失敗點；
- 模型輸出結構對不上 → **報錯**，不再靜默給 0 分（靜默的錯誤最危險）；
- 每一次呼叫都寫入 `ai_calls`，老師可以在「帳戶」頁看到成本與錯誤。
