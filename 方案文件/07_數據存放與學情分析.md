# 數據存放與學情分析

> 回答兩個問題：資料放在哪裡？要不要用 Supabase？
> 以及：錯題精煉是怎樣運作的。

---

## 一、資料放在哪裡

**全部在本機一個資料夾裡，沒有云服務，沒有外部資料庫。**

```
程式/data/
├─ app.db        ← SQLite 單一檔案（帳號、作業、分數、練習記錄）
├─ app.db-wal    ← 寫入中的交易日誌（正常，會自動合併）
└─ uploads/
   └─ <提交編號>/<雜湊>.jpg   ← 學生交的相片
```

備份 = 複製 `data/` 這一個資料夾。`node scripts/backup.mjs` 會用 SQLite 的
`VACUUM INTO` 做熱備份（不必關伺服器），再複製相片。

### 裡面有甚麼

| 表 | 存甚麼 | 大概欄位 |
|---|---|---|
| `roster` | 老師匯入的班級名單 | 班別、學號、姓名、學生證號碼 |
| `users` | 帳號 | 角色、登入名、密碼雜湊（scrypt） |
| `assignments` | 作業 | 題目與評分點（JSON）、截止、狀態、科目、學期 |
| `submissions` | 一份提交 | `ai_*`（AI 建議）與 `teacher_*`（老師定分）分開 |
| `answers` | 每題作答 | 文字、提交方式（打字／拍照）、AI 轉寫稿、老師修正稿 |
| `files` | 相片 | 路徑、大小、雜湊 |
| **`scores`** | **每題分數明細** | 學生、作業、知識點、得分、滿分（學情分析靠這張） |
| **`practice_items`** | **錯題練習題** | 知識點、題目、要點、示範答案 |
| **`practice_attempts`** | **練習作答記錄** | 答案、判斷（對／差一點／錯）、回饋 |
| `ai_calls` | 每次模型呼叫 | 用途、tokens、耗時、錯誤 |
| `audit` | 操作記錄 | 誰在何時做了甚麼 |

### 為甚麼要有 `scores` 這張表

分數原本只存在 `submissions.teacher_scores_json` 裡（一個 JSON）。
要算「這個學生『語言運用』這個知識點的得分率變化」，就得每次都拆 JSON——
慢、難寫、容易錯。

現在每次老師定分，系統會同步寫入 `scores` 一行一題，於是：

```sql
-- 某學生每個知識點、每份作業的得分率
SELECT tag, assignment_id, SUM(score) * 1.0 / SUM(max) AS rate
FROM scores WHERE student_id = ? AND source = 'teacher'
GROUP BY tag, assignment_id ORDER BY assignment_id;
```

## 二、需要 Supabase 嗎

**不需要。** 現階段用 SQLite 是刻意的選擇，不是權宜之計。

| | SQLite（現在） | Supabase／雲端 |
|---|---|---|
| 安裝 | 零（Node 內建） | 要開帳號、設環境變數、處理網絡 |
| 成本 | 0 | 免費額度夠，但要管理 |
| 資料在哪 | 你的電腦，一看就明 | 境外伺服器，要多寫一份私隱說明 |
| 備份 | 複製一個資料夾 | 要學他們的備份／還原流程 |
| 同時寫入 | 單機、一班 | 多機、多校 |
| 離線 | 完全可離線（除了 AI） | 斷網即停 |
| 換機器 | 複製資料夾 | 不用搬，但要重新配置 |

以你的規模（1 班、40 人、同一時間最多 40 個連線、每學期幾百份作業），
SQLite 的寫入能力遠遠有餘。實測寫入約 1ms（本機）、25ms（網絡磁碟）。

### 甚麼時候才真的要換

出現以下任何一項，才值得考慮：

1. **多過一間學校／多過一部伺服器**要同時寫入同一份資料；
2. 要讓**家長**由校外登入（需要 HTTPS + 對外服務，屆時也應該一併上雲）；
3. 資料量超過幾 GB（幾萬張相片）；
4. 要跟 eClass／WebSAMS 做即時雙向同步。

到那時也不是「換 Supabase 就完事」——`lib/db.js` 的 SQL 大部分可以直接搬，
但 `node:sqlite` 的同步 API 要改成非同步（`pg` 或 Supabase client），
大約半天到一天的工作量。**現在不需要預先做。**

> 一句話：先用最簡單的東西，把教學流程驗證完，再談基建。
> 過早引入雲端資料庫，只會令你多一個要維護的東西。

## 三、學情分析怎樣算

### 3.1 三個數字

- **得分率**（不是原始分）：`得分 ÷ 滿分`。跨作業比較一定要用得分率，
  因為每份作業滿分不同（12 分、16 分、20 分）。
- **知識點得分率**：同一 `tag` 的所有題目合計。
- **變化**：最近一次 vs 對上一次（不是 vs 第一次，避免一次失手就長期「退步」）。

### 3.2 甚麼時候不應該講「進步／退步」

**少於 3 次數據**，任何趨勢都是噪音。所以介面會直接寫明：

> 「只有 1 次數據。少於 3 次之前，『進步／退步』只供參考，不要當結論。」

這句話是刻意寫給老師看的——避免用兩個數據點就向家長說「你的孩子退步了」。

### 3.3 介面在哪

- 學生：`我的學習`（頂欄）→ 知識點由弱到強、每項的得分率、累計失分、可直接練習；
- 老師：`統計分析` → 學生列表點名字 → 同一個頁面（只讀，沒有練習按鈕）。

## 四、錯題精煉怎樣運作

### 4.1 資料流

```
老師定分
   └→ scores 寫入（每題一行，帶 tag）
        └→ 錯題清單：score < max 的題目，按 tag 分組，累計失分排序
             └→ 學生按「精煉練習」
                  ├→ 取出該 tag 最近 4 次扣分記錄
                  │   ├ 未做到的評分點（來自 AI 逐點分析）
                  │   ├ 原題（只作參考，不准照抄）
                  │   └ 學生原本的答案（看得出弱在哪裡）
                  ├→ 模型出 3 題：情境不同、考核能力相同、難度遞增
                  └→ 學生作答 → 即時判斷 → 具體回饋 + 示範答案
```

### 4.2 為甚麼不是「隨機出題」

因為隨機出題的練習，學生做完仍然不知道自己錯在哪。
這裡的每一題，都是**由學生自己未做到的那個評分點**長出來的。

實例（真實輸出）：

> 弱點：`提出具體的改法`
>
> 練習 1：You wrote 'The dog ran to the door.' You are least happy with the verb 'ran'.
> What exactly would you change?
>
> 練習 2：'The cookies were good.' You want the sentence to show how they tasted and smelled.
> Which part would you change, and what exact words would you add?

### 4.3 三個設計上的保險

1. **示範答案要答完才給**。API 在生成時不會回傳 `model_answer`，
   學生交了答案才看到——避免「未答先看答案」。
2. **答錯可以再交**，系統重新判斷。練習不是考試，目的是練到會。
3. **不計分**。練習成績不會進入任何分數記錄，只留作答歷史。

### 4.4 成本

一次生成 3 題約 1,700–2,400 tokens（10–13 秒）；每次批改約 400 tokens（1.5 秒）。
一個學生練 10 組，大約港幣一元的量級。

### 4.5 限制（要老實講）

- 生成的題目**可能重複同一個句式**，因為它針對同一個弱點；
- 判斷「差一點」與「未做到」的界線，模型仍會搖擺，所以要給回饋文字而不只是對錯；
- 練習只覆蓋「已批改過」的題目。如果老師沒批，就沒有弱點數據。

## 五、資料保留

- 全部留在本機，不上傳任何第三方（除了送去模型評分的那一份文字／相片）；
- 建議試用期滿後：`備份與匯出/備份.ps1` 匯出 → 刪除 `程式/data/`；
- 相片含學生手寫內容，屬個人資料，家長通告要寫明用途與保留期。

## 六、一個老師帶三個班（4A／4B／4C）

### 6.1 需要 database 嗎

**本來就已經有，而且三個班不需要任何額外東西。**
「班別」在資料庫裡只是一個文字欄位，三個班就是多幾行名單、多幾個 `class_name`。

粗算規模：3 班 × 35 人 ≈ 105 個帳號、每學期 8 份作業 ≈ 840 份提交、約 2,000 張相片。
SQLite 單檔處理這個量級毫無壓力（真正吃力的是網絡磁碟，見第二節）。

### 6.2 一份作業派給多個班

原本一份作業只屬於一個班，三個班就要開三份、改三次 rubric。現在改成多對多：

```sql
assignment_classes(assignment_id, class_name)
```

- 建作業時可以勾選「4A、4B、4C」，一份作業、一份評分標準；
- 之後改題目，三個班一齊改；
- 改派班別（例如 4B 換成 4C）也是一個勾選。

舊資料（只有 `assignments.class_name`）會自動補進這張表，所以升級不需要手動處理。

### 6.3 老師端多了三樣東西

1. **班別篩選**：作業頁頂部有「全部／4A／4B／4C」的篩選，並顯示各班已註冊／名單人數；
2. **分母按班**：一份派給 4A+4B 的作業，顯示「提交 5/70」而不是單一班的人數；
3. **逐班比較**：統計頁多一張表，同一份作業三個班的平均分與得分率並排——
   這是帶多班時最有用的一欄，一眼看到哪一班要跟進。

### 6.4 學生端的分隔

學生只會看到「派給自己班」或「沒有指定班別」的作業。
直接打開別班的作業網址會回 403，提交同樣被拒（已寫入測試）。

## 七、學生怎樣「收到」作業

### 7.1 現在的機制：登入就見到

沒有推送、沒有電郵、沒有通知。運作方式很簡單：

```
老師建作業 → 狀態設為「進行中」→ 學生下次登入，在「我的作業」就看到
```

學生首頁分兩區：**待完成**（未提交）與**已提交**。未交的排在前面，並顯示截止時間與剩餘狀態。
老師把狀態改回「草稿」，學生就即時看不到了（用來收作業或改期）。

### 7.2 為甚麼不做推送

- 學生沒有電郵（這是設計前提）；
- 學校不會為試用系統開放推送服務；
- 小學生看到通知就會即時處理的說法，本身不成立。

實務上真正有效的是**課堂上講一次 + 班群貼連結**。系統的角色是「一個固定網址，永遠有最新的作業」，
而不是「主動叫你交功課」。

### 7.3 已經做了的兩個提示

**1. 登入時彈一次「你有 N 份新作業」**

學生一登入就看到一個彈窗，列出未提交而且未看過的作業，按「知道了」就不再彈。

「未看過」記錄在資料庫（`assignment_views` 表），不是 localStorage——因為課室平板多人共用，
換一部機或清快取就不準。學生打開過該作業也會自動標記已看過，不會重複騷擾。

**2. 截止前 24 小時的橙色提示**

學生首頁頂部有一條橙色橫幅，列出 24 小時內截止、以及已逾期未交的作業，
並顯示「還有 3 小時」／「已逾期 5 小時」。提交之後即時消失。

兩者都只在學生登入後出現，不需要推送、不需要電郵、不會打擾老師。

### 7.4 仍然未做

- **班級 QR code**：老師投影一次，學生掃一次就入到登入頁，不用打網址（半小時可做）；
- 家長通知（要另外的通訊渠道）。

### 7.5 學生帳號是怎樣來的

不是老師逐個開帳號，而是：

```
老師匯入名單（班別、學號、姓名、學生證號碼）
   → 學生自己用「學生證號碼 + 姓名 + 班別 + 密碼」註冊
      → 系統核對名單，對得上才建立帳號
```

好處是老師不用保管密碼，也不會出現「老師幫學生設了密碼但學生忘了」的死循環。
壞處是**學生要自己註冊一次**——所以第一堂課要留 10 分鐘做這件事，
或者預先請班長協助。
